Block 1

Python execution model & the GIL

Every senior Python interview eventually gets here, because the GIL is the single most misunderstood piece of the language — interviewers use it to filter out candidates who've memorized "Python is slow" from candidates who actually understand what the GIL does and doesn't constrain.

001●●●●Near-certainCPython vs Python the language

Is "Python is interpreted" and "Python has a GIL" true of the language, or true of a specific implementation? Why does the distinction matter?

Both are properties of CPython, the reference implementation most people mean when they say "Python" — not inherent properties of the Python language specification itself. Other implementations exist: PyPy (JIT-compiled, often dramatically faster for long-running CPU-bound code), Jython/IronPython (compile to JVM/.NET bytecode), and notably no-GIL builds of CPython itself are now real and shipping (PEP 703, free-threaded CPython) rather than purely experimental. The distinction matters because interview answers that treat "the GIL" or "interpretation overhead" as immutable facts about Python miss that these are implementation choices — real, consequential ones for the vast majority of production code running on stock CPython, but not laws of the language itself.

Say it like this

"Both are properties of CPython specifically, not the language spec — PyPy is JIT-compiled and can be much faster for long-running CPU-bound work, and free-threaded CPython builds without the GIL are now real, not just a research proposal. In practice almost everyone's running stock CPython in production, so the GIL's constraints are very real day-to-day — I just wouldn't state them as immutable facts about 'Python' in an interview, since that's conflating the language with one implementation of it."

002●●●●Near-certainWhat the GIL actually does

Precisely explain what the GIL is and what specific problem it solves for CPython's implementation.

The Global Interpreter Lock is a single mutex that ensures only one thread executes Python bytecode at a time within a single process, regardless of how many OS threads exist. It exists because CPython's memory management isn't thread-safe by default — reference counting (the core mechanism behind CPython's garbage collection, covered in the next block) involves incrementing/decrementing a counter on every object reference, and doing that from multiple threads simultaneously without synchronization would cause race conditions leading to memory corruption (a refcount could be incremented and decremented concurrently, ending up wrong, causing premature frees or memory leaks). Rather than adding fine-grained locking around every object's refcount individually (which real attempts have shown adds significant single-threaded performance overhead), CPython takes the simpler, faster-for-the-common-case approach of one global lock around bytecode execution entirely.

Say it like this

"It's a single mutex ensuring only one thread runs Python bytecode at a time, and it exists specifically because CPython's reference counting isn't thread-safe on its own — incrementing and decrementing a refcount from multiple threads without synchronization would cause race conditions and actual memory corruption. The alternative would be fine-grained per-object locking, which real experiments have shown adds real single-threaded overhead, so CPython trades multi-core parallelism for simpler, faster single-threaded performance and a much simpler C API for extension authors to work with."

003●●●●Near-certainCPU-bound vs I/O-bound under the GIL

Why does threading help for I/O-bound Python code but not for CPU-bound code, given the GIL exists either way?

The GIL is released around blocking I/O operations (a network call, a file read, a `time.sleep`) — while one thread is waiting on I/O, it doesn't hold the GIL, so another thread can acquire it and run Python code during that wait. This means I/O-bound multithreaded code gets real concurrency benefit: while thread A waits on a network response, thread B can make progress. For CPU-bound code (a tight computational loop, pure Python number crunching), there's no I/O wait to release the GIL during — the GIL switches between threads periodically (CPython uses a check-interval-based or, more precisely since 3.x, a time-based switching interval), but only one thread is ever actually executing Python bytecode at any instant, so multiple CPU-bound threads don't run any faster in wall-clock time than one thread doing the same total work — often slightly slower, due to the overhead of the GIL handoff itself.

Say it like this

"The GIL gets released specifically around blocking I/O — while a thread's waiting on a network call or a file read, it's not holding the GIL, so another thread can run Python code during that wait, which is real concurrency for I/O-bound work. For CPU-bound code there's no I/O wait to release the GIL during — the interpreter does switch between threads periodically, but only one is ever actually executing bytecode at any given instant, so several CPU-bound threads don't get you more wall-clock throughput than one thread doing the same work, and you often pay a bit extra for the GIL handoff overhead itself."

004●●●○Very commonWhat "interpreted" actually means for CPython

Walk through what actually happens between running python script.py and code executing — is Python purely interpreted, with no compilation step at all?

No — CPython compiles source code to an intermediate bytecode representation first (viewable via the `dis` module), and it's that bytecode which gets interpreted by the CPython virtual machine, not the raw source text on every execution. This compiled bytecode is cached as `.pyc` files (in a `__pycache__` directory) so that re-running the same unchanged module skips recompilation on subsequent runs. This is meaningfully different from a "true" interpreted language that re-parses source text on every execution, and also different from a fully ahead-of-time compiled language producing native machine code — CPython sits in between, compiling to a portable bytecode format that's then interpreted by a virtual machine, conceptually similar in shape (though not implementation) to how the JVM works with Java bytecode.

Say it like this

"There's a real compilation step — source gets compiled to bytecode, and it's that bytecode the CPython VM actually interprets, not raw source text on every run. That bytecode gets cached as .pyc files in __pycache__ so unchanged modules skip recompilation on subsequent runs. So it's not purely interpreted in the naive sense of re-parsing text every time, and it's not ahead-of-time compiled to native code either — it's conceptually similar in shape to how the JVM interprets Java bytecode, just with CPython's own bytecode format and VM."

005●●●○Very commonEscaping the GIL for CPU-bound work

You have a genuinely CPU-bound Python workload that needs to use multiple cores. What are your actual options, and what does each cost?

Multiprocessing — separate OS processes, each with its own Python interpreter and GIL, giving genuine parallel execution across cores; the cost is inter-process communication overhead (data must be serialized/pickled to move between processes) and higher memory usage (no shared memory by default). C extensions that release the GIL — libraries like numpy perform their actual number-crunching in C code that explicitly releases the GIL during the computation, so Python threads calling into numpy can get genuine parallelism for that portion of the work even though it's "just threading" from the Python side; this is why numpy-heavy threaded code can scale across cores despite the GIL. Free-threaded CPython builds — an increasingly real option (PEP 703) for future-facing work, removing the GIL constraint entirely at the cost of the ecosystem still catching up on extension compatibility and some single-threaded performance overhead in the free-threaded build itself.

Say it like this

"Multiprocessing gives genuine parallelism since each process has its own interpreter and GIL, but you pay real serialization overhead moving data between processes and higher memory since there's no shared memory by default. C extensions that release the GIL during their actual computation, numpy being the classic example, let threaded Python code get real parallelism for that specific work even though it's nominally still under the GIL from Python's perspective. And free-threaded CPython builds are a real, increasingly viable option now, though I'd want to check ecosystem compatibility for whatever extensions the project actually depends on before committing to it in production."

006●●○○CommonGlobal vs per-interpreter state

Can a single process run multiple independent Python interpreters, each with its own GIL? Why would that matter?

Yes — CPython supports sub-interpreters, each historically sharing some global state but increasingly (as of recent PEPs, notably PEP 684) supporting per-interpreter GILs, meaning genuinely independent, parallel-capable interpreters within a single process, without the process-separation overhead multiprocessing requires. This is a newer, less commonly production-battle-tested area compared to multiprocessing, but it's the mechanism behind some emerging concurrency approaches that aim to get multiprocessing-like isolation and parallelism with lower overhead than spawning entirely separate OS processes — worth being aware exists, even if most current production code still reaches for multiprocessing or asyncio rather than sub-interpreters directly.

Say it like this

"Yes — sub-interpreters are a real CPython feature, and with per-interpreter GILs, which is a more recent development, you can get genuinely independent, parallel-capable interpreters within one process without the full overhead of separate OS processes. It's newer and less battle-tested in production than multiprocessing, so I wouldn't default to it yet for most workloads, but it's worth knowing it exists as the mechanism behind some emerging concurrency approaches, rather than assuming multiprocessing and threading are the only two options for real parallelism in CPython."

007●○○○OccasionalWhy the GIL hasn't just been removed

The GIL's downsides are well known. Why did it take until relatively recently for a real no-GIL CPython effort to succeed, given people have wanted this for decades?

Earlier attempts (going back to the mid-2000s "Gilectomy" project and others) ran into a genuine engineering trade-off: removing the GIL naively, via fine-grained locking, consistently caused significant single-threaded performance regressions — since the vast majority of Python code is single-threaded, a change that helps rare multithreaded CPU-bound workloads while slowing down the common case was a bad trade for the ecosystem as a whole. The successful modern effort (PEP 703) required years of preparatory work on CPython's internals — including changes to reference counting itself (biased reference counting) to make it safe and reasonably fast without the GIL's blanket protection — and required broad ecosystem buy-in, since C extensions written assuming the GIL's protections needed a path to remain correct without it. It's a genuinely hard, multi-year engineering and ecosystem-coordination problem, not a simple missing feature.

Say it like this

"Earlier attempts, going back to projects like the Gilectomy, kept hitting the same wall — naive fine-grained locking to remove the GIL consistently regressed single-threaded performance, and since almost all Python code is single-threaded, that's a bad trade for the ecosystem as a whole just to help a narrower multithreaded CPU-bound case. The effort that actually succeeded required years of deeper internals work, including changes to how reference counting itself works, to make it safe and reasonably fast without the GIL's blanket protection, plus real ecosystem coordination since C extensions built assuming the GIL needed a path to stay correct without it. It's a genuinely hard multi-year problem, not something that was just never prioritized."

Block 2

Memory management & object model

This block covers the mechanics behind the GIL discussion in Block 1 — how CPython actually manages memory, and the identity/equality distinctions that trip up even experienced Python engineers under interview pressure.

008●●●●Near-certainReference counting mechanics

Precisely explain how CPython's reference counting garbage collection works — when does an object actually get freed?

Every object carries an internal reference count — the number of references currently pointing to it. This count increments whenever a new reference is created (assigning to a variable, appending to a list, passing as a function argument) and decrements whenever a reference goes out of scope, is reassigned, or is explicitly deleted (`del`). The moment an object's reference count reaches zero, CPython immediately deallocates it — there's no delay, no separate garbage-collection pass required for this common case, which is why reference counting gives Python fairly predictable, immediate cleanup for the vast majority of objects, unlike a purely tracing/mark-and-sweep collector that runs periodically and independently of when an object actually became unreachable.

Say it like this

"Every object has a refcount tracking how many references point to it, incrementing on assignment or being passed around, decrementing when a reference is reassigned, goes out of scope, or is deleted. The moment that count hits zero, the object is freed immediately — no separate GC pass needed for that case, which is why cleanup is fairly deterministic and immediate for most objects in Python, unlike a purely tracing collector that runs periodically independent of when something actually became unreachable. This immediacy is also exactly why context managers and `with` blocks work so cleanly for resource cleanup in Python — you can rely on `__exit__` running right when the reference count-driven cleanup happens, not at some unpredictable future GC pass."

009●●●●Near-certainReference cycles

If reference counting frees objects immediately when their count hits zero, why does Python need a separate garbage collector at all?

Reference counting alone cannot detect reference cycles — two or more objects referencing each other (directly, or through a longer chain) such that their reference counts never reach zero even when nothing outside the cycle references them anymore (a classic case: a parent object holding a reference to a child, and the child holding a reference back to the parent). Without additional handling, these objects would leak forever, since pure refcounting has no way to recognize "this group of objects is mutually referencing itself but is otherwise unreachable." CPython's separate generational cyclic garbage collector (the `gc` module) periodically scans for exactly this pattern — groups of objects that are unreachable from any root except each other — and collects them, running independently of and in addition to the immediate refcount-based cleanup, specifically to handle the case refcounting structurally can't.

Say it like this

"Refcounting alone can't catch reference cycles — two objects referencing each other, directly or through a chain, keep each other's counts above zero even when nothing outside that cycle points to either of them anymore, a parent and child referencing each other back and forth being the classic case. Without something else handling that, those objects would just leak forever, since pure refcounting has no concept of 'this group is mutually self-referencing but otherwise unreachable.' The generational cyclic collector in the gc module runs periodically specifically to find and clean up exactly that pattern, on top of and independent from the immediate refcount-based cleanup that handles the non-cyclic majority of cases."

010●●●●Near-certainis vs ==

Precisely distinguish is and ==, and explain a realistic bug caused by confusing the two.

is checks identity — are these two names referring to the exact same object in memory (comparing memory addresses, effectively). == checks equality — is the value the same, using the object's own `__eq__` method, which can be arbitrarily defined by the type (two different `list` objects with the same elements are `==` but not `is`, since they're distinct objects that happen to hold equal values). A realistic bug: comparing against `None`, `True`, or `False` using `==` instead of `is` — this usually works by coincidence for singletons like `None` (there's only ever one `None` object, so `is None` and `== None` typically agree), but relying on `==` there is fragile if the object being compared has a custom `__eq__` that doesn't behave as expected against `None`, and idiomatic Python explicitly prefers `is None` for exactly this robustness reason, not just style.

Say it like this

"is checks whether two names point to the literal same object in memory — identity. == checks value equality via the object's own __eq__, which a type can define however it wants, so two separate list objects with identical contents are == but not is, since they're genuinely different objects that happen to hold equal values. The realistic bug is using == against None, True, or False — it usually works by coincidence since None is a singleton, but it's fragile if the object being compared has a custom __eq__ that doesn't behave the way you'd expect against None, which is exactly why 'is None' is the idiomatic, more robust check, not just a style preference."

011●●●○Very commonMutable default argument trap

Explain the classic mutable-default-argument bug, precisely why it happens, and the correct fix.

A function's default argument values are evaluated once, at function definition time — not freshly on every call. If a default is a mutable object (a `list`, `dict`, or any mutable type), every call that relies on that default shares the same object — mutating it in one call (appending to a default-`list` parameter, say) persists that mutation into subsequent calls, since they're all referencing the identical object created once at definition time, not a fresh one per call. The fix: use an immutable sentinel default (typically `None`), and create the actual mutable object inside the function body on each call if the default wasn't overridden — `def f(x=None): x = x if x is not None else []`.

// buggy — the list is created once, at def time, and shared across every call
def append_item(item, items=[]):
    items.append(item)
    return items

// correct — a fresh list is created inside the function on every call
def append_item(item, items=None):
    if items is None:
        items = []
    items.append(item)
    return items
Say it like this

"Default argument values are evaluated exactly once, at function definition time, not fresh on every call. So a mutable default like a list is the same actual object shared across every single call that relies on it — mutate it in one call and that mutation is still there the next time, since every call is referencing the identical object created once when the function was defined, not a new one per invocation. The fix is defaulting to None and creating the real mutable object inside the function body when the default wasn't overridden, so each call that needs the default actually gets a fresh object."

012●●●○Very commonSmall-int and string interning

a = 5; b = 5; a is b returns True. a = 500; b = 500; a is b can return False. What's actually going on?

CPython pre-allocates and caches a fixed range of small integers (typically -5 to 256) at interpreter startup as a performance optimization — since small integers are extremely common and immutable, reusing the same cached object for every occurrence of, say, `5` avoids repeatedly creating and destroying identical objects. Integers outside that cached range are ordinarily created as fresh, distinct objects each time (though the exact behavior can vary — the same literal appearing multiple times in the same compiled code object may get folded/deduplicated by the compiler, which is why `is` results here are officially implementation-detail, not language-guaranteed behavior). CPython does something conceptually similar for certain strings (short identifier-like strings are often interned). The senior-level takeaway: never rely on `is` for value comparison of ints or strings in real code — this caching behavior is a CPython implementation detail that can change between versions, not a guaranteed language feature to depend on.

Say it like this

"CPython caches a fixed range of small integers, typically -5 to 256, at startup, since small ints are extremely common and immutable, so reusing one cached object avoids constantly creating and destroying identical values. Outside that range, integers are ordinarily distinct objects, though the compiler can sometimes fold identical literals within the same code object, which is exactly why this is officially an implementation detail and not something the language guarantees. The actual takeaway I'd give is: never use is for value comparison on ints or strings in real code — this caching behavior is a CPython optimization that's changed before and could change again, not a language contract to build logic around."

013●●○○CommonDiagnosing a memory leak

A long-running Python service's memory usage grows steadily over days. Given Python has garbage collection, how is this possible, and how would you diagnose it?

"Has garbage collection" doesn't mean "can't leak" — genuine leaks still happen via: unbounded caches or global collections that keep growing and are never pruned (a module-level `dict` used as an ad-hoc cache with no eviction policy); reference cycles involving objects with `__del__` (historically genuinely uncollectable in older Python versions before improvements to the cyclic collector, though modern CPython handles most such cycles correctly now); lingering references held by something non-obvious — a logging handler, a callback registry, or a framework's internal state holding onto request-scoped objects longer than expected. Diagnosis: `tracemalloc` (built into the standard library) to snapshot and compare memory allocations over time, pinpointing exactly which lines of code are responsible for growing memory; `objgraph` or similar tools to visualize reference chains keeping specific objects alive when a suspected leaked type is known but the actual holding reference isn't obvious.

Say it like this

"Garbage collection prevents unreachable objects from leaking, it doesn't prevent something reachable from just never being released — an unbounded cache with no eviction policy, a logging handler or callback registry quietly holding onto request-scoped objects longer than it should, those are all real leaks despite GC working correctly. I'd reach for tracemalloc first, since it's built into the standard library and lets me snapshot allocations over time and see exactly which lines are responsible for growth, and if I know roughly what type is leaking but not what's holding the reference, something like objgraph to actually visualize the reference chain keeping it alive."

014●○○○Occasional__slots__ memory savings

How does defining __slots__ on a class reduce memory usage, and what capability does it give up?

By default, instances of a class store their attributes in a per-instance `__dict__` — a real dictionary, with real dictionary overhead (hash table structure, resizing, etc.) for every single instance, even for a class with just two or three simple attributes. Defining `__slots__` (a class-level declaration of the exact fixed set of allowed attribute names) tells CPython to allocate a more compact, fixed-size structure for instances instead of a full `__dict__`, meaningfully reducing per-instance memory overhead — genuinely significant when creating large numbers of instances of a simple class (millions of small objects, common in data-processing-heavy code). The trade-off: instances of a `__slots__` class can no longer have arbitrary attributes dynamically added at runtime — only the exact names declared in `__slots__` are allowed, which is a real behavioral change, not just an optimization with no observable effect, and can break code that relied on dynamically attaching ad-hoc attributes to instances.

Say it like this

"Normally every instance carries its own __dict__ for attribute storage, which has real dictionary overhead even for a class with just a couple of simple attributes. __slots__ declares the fixed set of allowed attributes upfront and lets CPython use a more compact fixed-size structure instead, which is a genuinely significant memory win when you're creating millions of small instances. The trade-off is real, not just an internal optimization — instances can no longer have arbitrary attributes dynamically added at runtime, only exactly what's declared in __slots__, so it can break code that relied on ad-hoc attribute attachment, which is why I wouldn't add it reflexively to every class without checking that behavior isn't relied upon somewhere."

Block 3

Data structures & their real complexity

Every senior Python engineer uses lists and dicts constantly, but this block checks whether they actually know the underlying complexity guarantees — the gap between "it works" and "it works efficiently at scale" often lives exactly here.

015●●●●Near-certainList complexity in practice

What's the time complexity of appending to a Python list, indexing into it, and inserting at the front — and why do these differ so much?

A Python `list` is implemented as a dynamic array (contiguous memory, not a linked list), which explains all three: indexing (`lst[i]`) is O(1), since contiguous memory allows direct offset calculation to any position. Appending (`lst.append(x)`) is amortized O(1) — CPython over-allocates extra capacity when it needs to grow the underlying array, so most appends just write into already-allocated space; occasionally a resize is needed (allocate a larger block, copy everything over), which is O(n) for that one operation, but averaged over many appends, the amortized cost per append stays constant. Inserting at the front (`lst.insert(0, x)`) is O(n) — because it's a contiguous array, inserting at the front requires shifting every existing element one position to make room, unlike a linked list where prepending is trivially O(1).

Say it like this

"A Python list is a dynamic array, contiguous memory, not a linked list, and that single fact explains all three. Indexing is O(1) because contiguous memory means direct offset calculation. Appending is amortized O(1) — CPython over-allocates extra capacity so most appends just write into space that's already there, occasionally paying an O(n) resize that gets averaged out over many appends. Inserting at the front is genuinely O(n), because with contiguous memory, making room at the front means shifting every single existing element over by one — which is exactly why I reach for a deque instead of a list whenever a workload needs frequent insertions or removals at the front."

016●●●●Near-certainDict lookup mechanics

Precisely explain how a dict achieves average O(1) lookup, and what has to be true of a key's type for it to work in a dict at all.

A `dict` is a hash table — a key's `__hash__()` method computes a hash value, which is used (via modulo against the table's current size, with collision resolution) to determine roughly where that key/value pair lives in the underlying array, allowing lookup, insertion, and deletion to compute a candidate location directly from the key rather than scanning — this is what gives average O(1) performance rather than the O(n) a linear scan would require. This requires keys to be hashable — which in practice means immutable for built-in types (a `tuple` is hashable, a `list` is not, precisely because a `list`'s contents, and therefore its hash, could change after being used as a key, which would break the hash table's internal consistency; a mutable key's hash changing after insertion would mean the dict could no longer find it at the location its now-stale hash pointed to). Worst-case dict operations degrade to O(n) under pathological hash collisions, though CPython's implementation and hash randomization make this rare in practice for typical workloads.

Say it like this

"A dict is a hash table — a key's hash value determines roughly where its entry lives in the underlying array, so lookup can compute a candidate location directly from the key instead of scanning everything, which is what gives average O(1) instead of O(n). That requires keys to be hashable, which for built-in types means immutable — a tuple works as a key, a list doesn't, specifically because a list's contents and therefore its hash could change after insertion, and if a key's hash changed after it was already placed based on the old hash, the dict would no longer be able to find it at the position that stale hash pointed to. Worst case does degrade to O(n) under pathological collisions, but CPython's hash randomization makes that a genuine edge case, not something I worry about for typical workloads."

017●●●○Very commonDict insertion order guarantee

Are Python dicts ordered? Has this always been true, and is it safe to rely on in production code?

As of Python 3.7, dict insertion order preservation is an official, guaranteed part of the language specification (it was an implementation detail of CPython 3.6 first, then formally guaranteed in 3.7) — iterating a dict yields keys in the order they were first inserted, and this is safe to rely on in any codebase targeting 3.7+. Before 3.6, dict order was genuinely unspecified and could vary. It's worth being precise that this guarantee is about insertion order, not sorted order — a dict doesn't sort its keys, it just remembers and preserves the sequence in which they were added, and re-inserting an existing key (updating its value) does not move it to the end — only genuinely new keys are appended to the iteration order; deleting and re-adding a key does move it, since that's a new insertion.

022●●●●Near-certainstr vs bytes

Precisely distinguish str and bytes in Python 3. Why was this split introduced, given Python 2 had a single string type that mostly worked?

str is a sequence of Unicode code points — an abstract representation of text, with no inherent byte-level encoding until you explicitly ask for one. bytes is a sequence of raw 8-bit values — the actual binary representation, with no inherent notion of "characters" at all until you explicitly interpret it as encoded text. Python 3 forces this distinction to be explicit everywhere — you must deliberately `.encode()` a `str` to `bytes` or `.decode()` `bytes` to a `str`, which eliminates an entire category of ambiguity-driven bugs at the cost of requiring genuinely more deliberate code.

025●●●○Very commonString concatenation in a loop

Why is repeatedly concatenating strings with += inside a loop considered a performance anti-pattern, and what's the correct alternative?

Python `str` objects are immutable — every `s += chunk` doesn't modify `s` in place, it creates an entirely new string object (copying all of `s`'s existing content plus the new chunk) and rebinds `s` to point to it. Repeating this `n` times means each iteration copies progressively more data, making the total cost O(n²) rather than the `O(n)` a naive reading might suggest. (Some CPython versions have an internal optimization that can make this faster in specific single-reference cases, but this is an implementation detail, not something to rely on or design around.) The correct, guaranteed-efficient alternative: accumulate pieces in a `list` and join them once at the end with `''.join(pieces)` — this is `O(n)` overall, since `join` can calculate the total needed size upfront and copy each piece exactly once, rather than repeatedly re-copying already-assembled content.

// O(n²) — creates a new string object on every iteration, copying everything so far
result = ""
for chunk in pieces:
    result += chunk

// O(n) — each piece is copied exactly once, in one final join
result = "".join(pieces)

028●●●●Near-certainLEGB scope resolution

Precisely explain Python's scope resolution order (LEGB), and walk through how it resolves a name reference inside a nested function.

LEGB — when Python encounters a name reference, it searches, in order: Local (the current function's own local scope), Enclosing (any enclosing function's scope, for nested functions — searched from innermost to outermost), Global (the module-level scope), Built-in (Python's built-in names like `len`, `print`). The search stops at the first scope where the name is found — a local variable shadows an enclosing or global variable of the same name, an enclosing variable shadows a global one, and so on. Critically, this resolution happens based on the lexical (textual) structure of the code — where a function is defined, not where it's called from — which is why a nested function can access its enclosing function's variables even if called from somewhere entirely different in the codebase, as long as it was defined inside that enclosing scope.

Say it like this

"LEGB — local first, then any enclosing function scope for nested functions, searched innermost to outermost, then the module-level global scope, then built-ins, and it stops at the first scope where the name's actually found, so a local shadows an enclosing variable of the same name, which shadows a global, and so on. The important detail is this is lexical scoping — it's based on where the function is defined in the code, not where it's called from, which is exactly why a nested function keeps access to its enclosing function's variables no matter where it ends up being invoked from later, as long as it was textually defined inside that scope."

029●●●●Near-certainLate binding closure trap

A loop creates several closures, each intended to capture the current value of the loop variable. Why do they all end up seeing the same final value instead, and how do you actually fix it?

Python closures capture variables by reference to the enclosing scope, not by value at the time the closure is created — a closure created inside a loop doesn't capture "the value the loop variable had at that iteration," it captures a reference to the loop variable itself, which continues to exist as one shared variable across all iterations of the loop. By the time any of the closures are actually called (typically after the loop has fully finished), the loop variable holds whatever its final value was — so every closure, when invoked, looks up that same shared variable and sees the same final value, not the value from "their" iteration. The fix: force the value to be captured at closure-creation time by binding it as a default argument (default arguments are evaluated once, at function-definition time — the same mechanism behind the mutable-default-argument bug from Block 2, just being used deliberately here to solve a different problem).

// buggy — all closures share and reference the same loop variable
funcs = []
for i in range(3):
    funcs.append(lambda: i)
[f() for f in funcs]  # [2, 2, 2] — not [0, 1, 2]

// fixed — default argument captures the value at creation time, per iteration
funcs = []
for i in range(3):
    funcs.append(lambda i=i: i)
[f() for f in funcs]  # [0, 1, 2]

034●●●●Near-certain__init__ vs __new__

Precisely distinguish __new__ and __init__ — what does each actually do, and when would you need to override __new__?

__new__ is responsible for creating the instance — it's a static method (implicitly) that allocates and returns a new object, and it's called before the instance exists. __init__ is responsible for initializing an already-created instance — it receives the object `__new__` already returned (as `self`) and sets up its initial state (assigning attributes), but doesn't create or return anything itself. For the vast majority of classes, `__new__` is never overridden at all — the default inherited from `object` handles instance creation fine, and `__init__` is where all the real customization happens. 045●●●●Near-certainIterator protocol precisely

Precisely distinguish an iterable from an iterator, and explain exactly what a for loop does mechanically under the hood.

An iterable is any object implementing `__iter__`, which returns an iterator. An iterator is any object implementing both `__iter__` (returning itself) and `__next__` (returning the next value each call, raising `StopIteration` when exhausted). A `for` loop mechanically: calls `iter(the_iterable)` once at the start to get an iterator, then repeatedly calls `next()` on that iterator object until `StopIteration` is raised, at which point the loop ends cleanly. This is precisely why an iterator itself (as opposed to a re-iterable collection) can only be consumed once — calling `iter()` on an iterator just returns itself, with whatever position it was already at, so a `for` loop over an already-partially-consumed iterator picks up from where it left off, not from the beginning.

046●●●●Near-certainGenerator laziness and state suspension

A function containing yield behaves completely differently from a normal function when called. Precisely explain what actually happens, and why generators are memory-efficient for large sequences.

Calling a generator function doesn't execute the function body at all — it immediately returns a generator object (which is itself an iterator, implementing `__next__`), with the function's code not yet run. Each call to `next()` on that generator object runs the function's body until the next `yield` statement, at which point execution suspends — the entire local state (variable values, the exact position in the code) is preserved — and the yielded value is returned to the caller. 051●●●●Near-certainHow the event loop actually works

Precisely explain what the asyncio event loop actually does — how does a single thread run "concurrent" code at all?

The event loop is a single-threaded scheduler that runs one coroutine at a time, but switches between multiple coroutines at points where they explicitly yield control back to the loop — every `await` is a potential switch point, where the currently-running coroutine says "I'm waiting on something (I/O, a timer, another coroutine), you can run something else until this is ready." The loop maintains a queue of ready-to-run tasks and callbacks, and repeatedly: picks the next ready task, runs it until it hits an `await` on something not yet complete, parks it, and moves to the next ready task — this is cooperative multitasking, fundamentally different from OS-level thread preemption, since a coroutine only yields control voluntarily at an `await` point, never being forcibly interrupted mid-execution the way a thread can be. This is exactly why a single blocking (non-async) call inside a coroutine — a synchronous `time.sleep()` instead of `asyncio.sleep()`, a synchronous database call — genuinely freezes the entire event loop, since nothing else can run until that blocking call finally returns control, unlike a thread being blocked, which doesn't prevent other threads from being scheduled.

Say it like this

"It's a single-threaded scheduler running one coroutine at a time, switching between them at explicit yield points — every await is a potential switch point where the running coroutine says 'I'm waiting on something, run something else until it's ready.' 058●●●●Near-certainChoosing between threading, multiprocessing, and asyncio

Given a workload, how do you decide between threading, multiprocessing, and asyncio? Walk through the actual decision criteria.

The decision hinges on the workload's actual bottleneck. I/O-bound work with a smaller number of concurrent operations, or when integrating with libraries that are genuinely synchronous/blocking with no async-native alternative available (common with many older or less actively maintained libraries), often fits threading best — since the GIL releases around I/O, threads still get real concurrency benefit for I/O-bound work, without needing to rewrite blocking library calls to be async-compatible.

059●●●●Near-certainMultiprocessing IPC cost

You parallelize a CPU-bound task across multiple processes, but the speedup is much smaller than expected — sometimes even slower than single-process. What's the likely cause?

Separate processes don't share memory by default — any data passed into a worker process and any result passed back has to be serialized (via `pickle`, by default) and sent through inter-process communication, which has real, non-trivial overhead. 061●●●○Very commonRace conditions despite the GIL

Given the GIL ensures only one thread runs Python bytecode at a time, why can multithreaded Python code still have genuine race conditions?

The GIL guarantees only one thread executes Python bytecode at any single instant, but it does not guarantee that a higher-level operation composed of multiple bytecode instructions executes atomically as a whole — the GIL can be released and reacquired (switching to another thread) between individual bytecode instructions, mid-way through what looks like a single line of Python code. A classic example: `counter += 1` is actually multiple bytecode operations (load current value, add one, store new value) — if two threads interleave between those steps (thread A loads the value, gets switched out before storing, thread B loads the same now-stale value and increments it, then thread A resumes and stores its own now-stale increment, overwriting thread B's update), the final result is wrong, a genuine lost-update race condition, despite the GIL. This is exactly why shared mutable state accessed from multiple threads still needs explicit synchronization (a `threading.Lock`) around any multi-step read-modify-write sequence — the GIL protects individual bytecode instructions from corrupting each other, not the logical correctness of a sequence of them taken together.

062●●○○Commonfork vs spawn start methods

064●●●●Near-certainType hints have no runtime effect

Does adding a type hint to a function parameter actually enforce that type at runtime? What's the real relationship between type hints and runtime behavior?

This means a codebase can have perfectly clean type hints and still hit a runtime `TypeError` if the static type checker was never actually run in CI, or if code violates its own type hints in a way the checker didn't happen to catch (dynamic code the checker can't fully analyze, or a deliberate `# type: ignore`) — type hints are a real and valuable static-analysis tool, but they are not, on their own, a runtime safety guarantee.

066●●●○Very commonProtocol vs ABC for typing

An ABC requires explicit inheritance — a class must actually subclass the ABC (or be explicitly registered as a "virtual subclass") to satisfy that type, which means retrofitting type-checking onto code using third-party or existing classes that weren't written to inherit from your ABC is genuinely awkward or impossible without modifying those classes. `typing.Protocol` implements structural typing ("static duck typing") — any class with the right method signatures satisfies the protocol, with no inheritance relationship required at all, matching how idiomatic Python duck typing actually works at runtime, but now with static type-checker support. 071●●●●Near-certainWhat a with block actually guarantees

Precisely explain what with resource() as r: actually does, and what guarantee it provides that a manual try/finally wouldn't give you for free.

You need a simple context manager but writing a full class with __enter__/__exit__ feels like overkill. What does @contextlib.contextmanager let you do instead, and how does it work?

`@contextlib.contextmanager` lets you write a context manager as a generator function with a single `yield` — code before the `yield` becomes the effective `__enter__` logic (runs on entering the `with` block), the yielded value becomes what's bound by `as`, and code after the `yield` becomes the effective `__exit__` logic (runs on exiting the block, wrapped in a `try`/`finally` internally so it reliably runs even if the block's body raises). Why is a bare except: (with no exception type specified at all) considered a genuine anti-pattern, beyond just being "too broad"?

084●●●○Very commonWhy numpy is faster than pure Python loops

Numerically identical code runs dramatically faster in numpy than in a pure Python loop doing the same math. Precisely explain why.

A pure Python loop processing a list pays real per-element overhead: each iteration involves bytecode dispatch through the interpreter loop, type checking (Python is dynamically typed, so every operation re-checks what type it's operating on), and working with boxed objects (a Python int or float is a full heap-allocated object with reference counting overhead, not a raw machine value). Numpy arrays store data as a contiguous block of raw, unboxed machine-native values (a true C array of actual floats/ints, not Python objects wrapping them), and numpy's operations are implemented in compiled C code that operates directly on that raw memory in a tight loop with no per-element Python interpreter overhead, no repeated type checking, and often taking advantage of SIMD (processing multiple values in a single CPU instruction) and cache-friendly contiguous memory access patterns a Python list of boxed objects scattered across the heap can't offer.

Say it like this

"A pure Python loop pays real per-element overhead — bytecode dispatch through the interpreter, dynamic type checking on every operation, and working with boxed objects, since a Python int isn't a raw machine value, it's a full heap-allocated object with reference counting. Numpy stores data as a contiguous block of raw, unboxed native values, an actual C array, and its operations are compiled C code running in a tight loop directly on that memory with none of that per-element overhead — no interpreter dispatch, no type checks, often genuine SIMD use and much better cache locality since the data's actually contiguous in memory rather than scattered Python objects on the heap. That combination is why the speedup is often two or three orders of magnitude, not a modest improvement."

085●●●○Very commonfunctools.lru_cache

When is @functools.lru_cache a genuinely good optimization, and where can it actually backfire?

Good fit: a pure function (deterministic — same inputs always produce the same output, no side effects) that's called repeatedly with the same arguments and where the computation itself is genuinely expensive relative to a cache lookup — classic cases include recursive computations with overlapping subproblems (Fibonacci-style memoization) or expensive I/O-free calculations called with a small, repeating set of inputs. Where it backfires: caching a function whose result should reflect changing external state (silently returning stale data instead of a fresh computation); caching a function called with a huge variety of distinct arguments (the cache grows essentially unbounded, consuming real memory for entries that are each only used once, providing no actual hit-rate benefit); and — a real, easy-to-miss gotcha — caching a method on a class without care can inadvertently keep the entire self instance alive indefinitely via the cache's own internal reference, creating a memory leak by preventing otherwise-unreferenced instances from being garbage collected.

Say it like this

"It's a great fit for a pure, deterministic function called repeatedly with the same arguments where the computation is genuinely expensive relative to a cache lookup — recursive memoization is the classic case. Where it backfires: if the function's result should reflect changing external state, you're now silently serving stale data. If it's called with a huge variety of distinct arguments, the cache just grows unbounded with mostly single-use entries, real memory cost for no actual hit-rate benefit. And the gotcha I actually watch for is caching an instance method without care — the cache holds a reference to self internally, which can keep instances alive indefinitely and become a genuine memory leak, since normal garbage collection can't reclaim something the cache is still referencing."

086●●○○CommonCython & native extensions

You've profiled and found a genuine CPU-bound bottleneck in pure Python that numpy vectorization can't address (complex, branchy per-element logic). What are your realistic options?

Cython — a superset of Python that compiles to C, letting you add optional static type declarations to Python-like code for a significant, often dramatic speedup on exactly this kind of branchy, hard-to-vectorize logic, while staying much closer to Python syntax than writing a C extension by hand; a common, pragmatic approach is writing normal Python first, profiling, and only adding Cython type annotations to the specific hot function once identified, rather than rewriting the whole module. Rewriting the hot path in C/Rust as a native extension — more upfront effort and a genuinely different skillset, but can offer more control and, for Rust specifically (via PyO3), memory safety guarantees a hand-written C extension doesn't have. Numba — a JIT compiler that can accelerate specific numerically-heavy Python functions with a simple decorator, often requiring less code restructuring than Cython for pure numerical code, though generally more limited to numerical/array-heavy code than Cython's broader applicability. The senior-level judgment: reach for these only after confirming (via profiling) that the bottleneck is real, isolated, and can't be addressed by a simpler algorithmic or data-structure change first — introducing a compiled-extension build step is real, ongoing complexity that should be justified by a measured need, not adopted preemptively.

Say it like this

"For genuinely branchy per-element logic that vectorization can't help with, Cython is usually my first look — you can write close to normal Python and add static type declarations just to the hot function once profiling's actually identified it, rather than rewriting the whole module upfront. Numba's a JIT option that can work with less restructuring for pure numerical code specifically, though it's more narrowly scoped than Cython. A full native extension in C or Rust is the heavier option, more control and for Rust specifically real memory safety guarantees via PyO3, but a genuinely different skillset and more upfront investment. 087●○○○OccasionalMemory profiling vs CPU profiling

A service's memory usage keeps growing over time (a suspected leak), but CPU usage looks fine. How would you approach this differently from a CPU performance investigation?

This needs a fundamentally different tool category — a CPU profiler tells you where time is spent, but says nothing about what's holding memory alive. A memory profiler (tracemalloc, part of the standard library, or third-party tools like memory_profiler or objgraph) is needed to track object allocations over time and identify what's accumulating. Since CPython uses reference counting, a genuine "leak" (as opposed to a language with manual memory management) almost always means something is unintentionally holding a reference to objects that should otherwise be eligible for collection — a growing cache with no eviction policy, a module-level list that keeps appending without ever clearing, event listeners/callbacks registered but never unregistered, or (as covered in the caching question) an lru_cache-decorated method inadvertently keeping instances alive. The diagnostic process is fundamentally about finding what's still referencing the objects that should have been freed, not about execution speed at all.

Say it like this

"This is a genuinely different investigation from a CPU issue — a CPU profiler tells you where time goes, nothing about what's holding memory alive. I'd reach for tracemalloc, built into the standard library, to actually track allocations over time and see what's accumulating. Since CPython uses reference counting, a real leak almost always means something's unintentionally still holding a reference to objects that should be collectible — an unbounded cache with no eviction, a module-level list that keeps growing, callbacks registered but never cleaned up.
